# kulisa-ffmpeg

A minimal LGPL build of FFmpeg for Windows x64, made for the transcode stage of the Kulisa restream
feature. It is built by cross compilation in Docker (Ubuntu 24.04 with mingw-w64) and released as a
zip of shared libraries plus the matching source archive.

Source code of the build: https://github.com/PhoenixllGames/kulisa-ffmpeg

## What it does

Kulisa starts `ffmpeg.exe` as a child process. Kulisa writes FLV to its standard input and reads FLV
from its standard output; the relay in Kulisa owns the network, so FFmpeg is built without network
support and without TLS, and stream keys never appear on its command line.

Typical use:

```
ffmpeg -f flv -i pipe:0 -vf scale=-2:720,fps=30 -c:v h264_mf -rate_control cbr -b:v 3000k -maxrate 3000k -bufsize 6000k -g 60 -bf 0 -c:a copy -progress pipe:2 -f flv pipe:1
```

## NVENC driver requirement

The NVENC API level of the nv-codec-headers decides the minimum NVIDIA driver. This build uses
nv-codec-headers 11.1.5.4 (Video Codec SDK 11.1), which needs a Windows driver 471.41 or newer; with
an older driver `h264_nvenc` fails to open and reports that the driver does not support the required
nvenc API version. NVIDIA keeps the NVENC API binary backward compatible, so current drivers work as
well.

FFmpeg 9.0.2 configure accepts three ranges of ffnvcodec: 11.1.5.3 up to below 12.0, 12.0.16.1 up to
below 12.1, and 12.1.14.0 or newer. The 11.1 headers keep everything the 8-bit 4:2:0 H.264 transcode
uses (CBR and VBR rate control, `-g`, `-bf`, presets p1 to p7, tune, profiles baseline, main and
high), plus `h264_cuvid`, `h264_nvdec`, `hwupload_cuda` and `scale_cuda`. Newer headers add H.264
features this build does not use (high10, high422, `tf_level`, `lookahead_level`, timecode SEI) and
raise the minimum driver: 12.0.16.x needs 522.25, 12.1.14.x needs 531.61, 12.2.72.0 needs 551.76,
13.0.19.1 needs 570.0, 13.1.15.0 needs 610.0. Changing `NV_CODEC_HEADERS_*` in `versions.env` and the
build number is the only change needed.

## Contents of the build

Everything else is disabled (`--disable-autodetect --disable-everything`). The allow list is the file
`components`; a later addition is a one-line change there.

- Programs: `ffmpeg` only.
- Libraries: avutil, avcodec, avformat, avfilter, swscale, swresample, avdevice (lavfi input only).
- Protocols: pipe only (no file access, no network). Demuxers: flv, live_flv. Muxers: flv, null.
  Input device: lavfi.
- Decoders: h264, aac, h264_qsv, h264_cuvid, wrapped_avframe.
- Encoders: h264_mf, h264_nvenc, h264_amf, h264_qsv, aac, wrapped_avframe.
- Hardware acceleration: Media Foundation, NVENC, NVDEC and CUVID through ffnvcodec, CUDA kernels
  compiled with clang (cuda-llvm), AMF, QSV through libvpl, D3D11VA. There is no DXVA2 (D3D9) path.
  `ffmpeg -hwaccels` lists d3d11va, cuda, qsv and amf.
- Hwaccels: h264_d3d11va, h264_d3d11va2, h264_nvdec.
- Parsers: h264, aac. Bitstream filters: aac_adtstoasc, h264_mp4toannexb, extract_extradata, null.
- Filters: scale, fps, format, null, anull, aresample, aformat, setpts, asetpts, trim, atrim, copy,
  hwupload, hwdownload, hwmap, hwupload_cuda, scale_cuda, scale_qsv, vpp_qsv, vpp_amf, scale_d3d11,
  color, testsrc2, nullsrc, anullsrc, sine. FFmpeg adds the filters its own command line tool needs
  (crop, hflip, vflip, transpose, rotate).
- Disabled defaults: `faan` (floating point AAN DCT). It is the only selector of `fdctdsp` here, so
  the IJG forward DCT (`jfdctfst.c`, `jfdctint.c`) is not built. `idctdsp` with the IJG inverse DCT
  (`jrevdct.c`) stays: the h264 decoder suggests `error_resilience`, which selects `me_cmp`, which
  selects `idctdsp`, and configure has no switch to drop it without changing the FFmpeg source.

The binaries import only Windows system DLLs and each other (no libwinpthread, libgcc or libstdc++
DLLs). The check runs at the end of every build and fails the build otherwise.

## Intel QSV runtime search (libvpl dispatcher)

`h264_qsv`, `scale_qsv`, `vpp_qsv` and the QSV device go through the statically linked libvpl
dispatcher. When a QSV session starts, the dispatcher looks for Intel runtime DLLs and loads every
candidate it finds (which runs its `DllMain`) in these places, in this order:

1. the directories in the `ONEVPL_PRIORITY_PATH` environment variable;
2. the Windows driver store of the installed Intel graphics driver;
3. the directory of `ffmpeg.exe`;
4. every directory in `PATH`;
5. the directories in the `ONEVPL_SEARCH_PATH` environment variable;
6. the legacy Media SDK locations: the driver store, the directory named by the dispatcher registry
   key under `HKEY_CURRENT_USER`, then the one under `HKEY_LOCAL_MACHINE`, then `%windir%\System32`.

Rule for Kulisa: spawn `ffmpeg.exe` (the transcode and every encoder probe) with an explicit
environment, with `PATH` limited to the ffmpeg `bin` directory and `%SystemRoot%\System32`, and without
the `ONEVPL_PRIORITY_PATH` and `ONEVPL_SEARCH_PATH` variables. The driver store and the registry
locations stay, as for every application that uses QSV.

## Configure line

This is the line `ffmpeg -buildconf` reports (the build number does not change it):

```
./configure \
  --prefix=/opt/kulisa-ffmpeg --arch=x86_64 --target-os=mingw32 --cross-prefix=x86_64-w64-mingw32- \
  --pkg-config=pkg-config --pkg-config-flags=--static --x86asmexe=nasm \
  --enable-shared --disable-static --disable-autodetect --disable-everything \
  --disable-debug --disable-doc --disable-network --disable-programs \
  --extra-ldflags=-static-libgcc --extra-ldflags=-static-libstdc++ \
  --extra-ldflags='-Wl,--no-insert-timestamp' --extra-libs=-lstdc++ \
  --enable-ffmpeg \
  --enable-protocol=pipe --enable-demuxer='flv,live_flv' --enable-muxer='flv,null' \
  --enable-indev=lavfi \
  --enable-decoder='h264,aac,h264_qsv,h264_cuvid,wrapped_avframe' \
  --enable-encoder='h264_mf,h264_nvenc,h264_amf,h264_qsv,aac,wrapped_avframe' \
  --enable-hwaccel='h264_d3d11va,h264_d3d11va2,h264_nvdec' \
  --enable-parser='h264,aac' \
  --enable-bsf='aac_adtstoasc,h264_mp4toannexb,extract_extradata,null' \
  --enable-filter='scale,fps,format,null,anull,aresample,aformat,setpts,asetpts,trim,atrim,copy,hwupload,hwdownload,hwmap,hwupload_cuda,scale_cuda,scale_qsv,vpp_qsv,vpp_amf,scale_d3d11,color,testsrc2,nullsrc,anullsrc,sine' \
  --enable-ffnvcodec --enable-nvenc --enable-nvdec --enable-cuvid --enable-cuda-llvm \
  --enable-amf --enable-libvpl --enable-mediafoundation --enable-d3d11va \
  --enable-w32threads --disable-faan
```

The line is assembled by `scripts/build-ffmpeg.sh` from `components`.

## Release assets

| Asset | Content |
|---|---|
| `kulisa-ffmpeg-<tag>-win64.zip` | `bin/ffmpeg.exe` and the FFmpeg DLLs, `LICENSE.txt` (FFmpeg COPYING.LGPLv2.1), `BUILDINFO.txt`, `licenses/` |
| `kulisa-ffmpeg-<tag>-src.tar.xz` | the files of this repository at the tagged commit, `toolchain-dpkg-l.txt` (the full `dpkg -l` of the toolchain image) and `sources/` with every source tarball the build used, unmodified (FFmpeg with its signature and the release key, nv-codec-headers, AMF headers, libvpl) |
| `SHA256SUMS` | SHA-256 of the two files above |

Both archives are deterministic: sorted entries, fixed owners and modes, and the fixed timestamp
`SOURCE_DATE_EPOCH` from `versions.env`. The PE headers carry the same fixed timestamp.

## Rebuild

Needs Docker. In a git checkout:

```
./build.sh
```

`build.sh` builds from the committed tree (`git archive HEAD`) and refuses a dirty working tree, so
the source archive never holds uncommitted files. It first builds the toolchain image
`kulisa-ffmpeg-toolchain:noble-<APT_SNAPSHOT>` (apt from the pinned snapshot), then the assets on top
of it, without the Docker build cache. Sources that are not in `sources/` are downloaded; every source
is verified against the SHA-256 values in `versions.env`, and the FFmpeg tarball also against its GPG
signature and the pinned release key fingerprint, whether it was downloaded or pre-seeded.

The assets are written to `dist/`. Files are copied out of the container with `docker create` and
`docker cp`, so they are owned by the calling user.

| File | Role |
|---|---|
| `versions.env` | pinned versions, URLs, SHA-256 values, base image digest, apt snapshot, `BUILD_NUMBER` |
| `components` | the allow list of FFmpeg components and external libraries |
| `Dockerfile` | toolchain, build and package stages |
| `scripts/fetch.sh` | verification (and download, when not pre-seeded) of the sources |
| `scripts/build-deps.sh` | nv-codec-headers, AMF headers and static libvpl |
| `scripts/build-ffmpeg.sh` | configure, make, install, notices |
| `scripts/notices.py` | third party notices of the compiled FFmpeg code |
| `scripts/package.sh` | import check, `BUILDINFO.txt`, licenses, zip and source archive |
| `verify.ps1` | checks of a built zip on Windows |

## Reproduce a release offline

The source archive of a release rebuilds the same assets without network access:

```
mkdir rebuild && tar -xJf kulisa-ffmpeg-<tag>-src.tar.xz -C rebuild
cd rebuild/kulisa-ffmpeg-<tag>-src
./build.sh            # with network: builds the toolchain image from the apt snapshot (and the assets)
./build.sh --offline  # the assets again, with docker build --network none
cd dist && sha256sum -c <path to the published SHA256SUMS>
```

Outside a git checkout `build.sh` takes the files of the extracted archive, uses its `sources/`
directory (verified as above) and compares the package list of the toolchain image with the
archive's `toolchain-dpkg-l.txt`; a different package set stops the build. `--offline` needs the
toolchain image `kulisa-ffmpeg-toolchain:noble-<APT_SNAPSHOT>` to exist already (from a build with
network, or loaded with `docker load`) and runs every build step with `--network none`. Both runs
give byte-identical assets.

## Verify a build on Windows

`verify.ps1` extracts the zip into an empty directory and checks:

- the license text, the configure line (no gpl, nonfree or version3, and `BUILDINFO.txt` equal to
  `-buildconf`), the files of the zip and the notices (the IJG sentence, the mingw-w64 ZPL and
  Lucent notices);
- the encoders (exactly the allow list), the hwaccels (exactly d3d11va, cuda, qsv and amf) and the
  filters of the allow list, compared by exact name from the name column of each listing;
- an FLV transcode through standard input and output with `h264_mf` (`-hw_encoding 0` and `1`);
- a one-frame probe of each GPU encoder.

A GPU probe and the `-hw_encoding 1` run may fail on a machine without that GPU, but only cleanly:
a negative AVERROR exit code and a known FFmpeg error line in stderr. An NTSTATUS exit code (a crash
or a missing DLL, such as 0xC0000005 or 0xC0000135) or an empty stderr fails the check.

A separate ffmpeg and ffprobe, used only to create the test input and inspect the output, is passed
with `-GplBin`; it is not part of this build.

```
pwsh ./verify.ps1 -Zip dist/kulisa-ffmpeg-v9.0.2-1-win64.zip -Dest D:\tools\kulisa-ffmpeg-v9.0.2-1 -GplBin <dir with ffmpeg.exe and ffprobe.exe>
```
